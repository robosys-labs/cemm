fix: greeting recognition, AmbiguousReferent handling, and learning loop

Three issues traced from the web demo:

1. GREETING MISCLASSIFICATION ("hi" -> report_target_uncertainty)
   - Root cause: The only greeting training example was "@A0<event_type>."
     (with period). "hi" has no period, so the classifier predicted
     force=query (op:state about event:greeting) instead of force=claim
     (op:event greeting). The greeting check in the runtime never fired.
   - Fix: Added no-period greeting examples (Hi, Hello, Hey / Hola) to
     en_seed.json, es_seed.json, and the compiled language packs.
     Recomputed pack hashes.

2. UNCAUGHT AmbiguousReferent FROM observe()
   - Root cause: The delexer can raise AmbiguousReferent during observe()
     (e.g. "hello" maps to both event:greeting and value:greeting_ack),
     but the runtime only caught it around compose(). This crashed the
     web demo.
   - Fix: Wrapped the observe() call in process() with a try/except that
     creates a frontier, runs a clarify goal through the arbiter, and
     returns a proper request_targeted_clarification response with a
     complete Stage 0-22 trace.

3. LEARNING LOOP (name frontier never resolves)
   - Root cause: Normal conversation intentionally cannot admit new
     concepts (no concept fallback, per the final architecture). But the
     web demo only exposed normal/read_only modes, giving the user no
     way to teach new words. Frontiers were persisted but never
     consultable.
   - Fix: Added /api/acquire endpoint wrapping acquire_reviewed() so
     users can admit new concepts with explicit semantic kinds. Updated
     the web UI with a "Teach new word" panel (surface + kind selector)
     and a "Reviewed teach" mode in the chat mode dropdown.
